# T1.2 — Gateway trusted-identity coverage for medical routes

**Status:** ✅ DONE (static) · **Size:** M · **Priority:** 🔴 P0
**Source:** BUSINESS_FLOW_SOURCE.md §6.1 row 6, §11.7 row 2, §10 Final P0 row 1
**Verdict:** 🟢 gateway gap mitigated by downstream JWT re-verification + header stripping · ❌ F1-001 (notifications have neither)

## Results (08/07/2026)

**The doc's gateway finding is technically still present but NO LONGER exploitable for clinical
data**, because defense moved to the services:

- `requiresTrustedIdentity()` (`proxy.middleware.ts:79-85`) still only forces a token for
  `booking-langgraph-service`, `/api/v1/appointments`, `/api/v1/patient-representatives`.
- **BUT** every downstream clinical/payment controller applies its own `JwtAuthGuard`
  (`clinical-emr/auth/jwt-auth.guard.ts`) which **re-verifies the HS256 signature itself** using
  `AUTH_JWT_SECRET` (`actor.util.ts` — the file comment explicitly says it must not trust
  gateway-forwarded headers). So a tokenless request to `/api/v1/patients` gets 401 at the service.
- **Header spoofing is blocked:** the gateway unconditionally **deletes** inbound
  `x-auth-user-id`/`x-patient-id`/`x-auth-role` (`proxy.middleware.ts:175-177`) before injecting
  verified ones. A client cannot forge `x-auth-role: ADMIN`.

**The one hole:** `notifications` / `notification-templates` / `notification-preferences`
(iam-service) have **no controller guard** (see T1.3) AND the gateway doesn't require identity for
their prefixes (`services.config.ts:52-54`). → **F1-001 (🔴)**, the only place both layers are absent.

**Recommendation:** flip `requiresTrustedIdentity()` to default-true with an explicit public
allowlist (health, `/api/v1/auth`, `payments/vnpay-return` IPN, public booking availability), so a
future unguarded controller can't silently become public like notifications did.
