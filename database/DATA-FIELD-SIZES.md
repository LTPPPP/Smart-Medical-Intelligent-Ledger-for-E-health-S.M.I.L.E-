# Data Field Sizes

This document explains **why** each column in the SMILE database has its current size (e.g. why money is `NUMERIC(12,2)`, etc.). It applies to the schemas in `database/**/schema.sql` and the corresponding TypeORM migrations.

---

## 0. The most important principle about `VARCHAR(n)` in PostgreSQL

Before reading the table below, understand this key point:

> In PostgreSQL, `VARCHAR(n)` does **NOT** pre-allocate `n` bytes. It stores exactly the actual string length (identical to `TEXT`), plus one **length-constraint check** on write. There is no performance or storage difference between `VARCHAR(50)` and `VARCHAR(500)` for the same string.

So the number `n` here is **not about saving disk space** — it is a **business guardrail (business validation)**:

1. **Block junk / attacks** — nobody can stuff 10MB into a "name" field.
2. **Express intent** — `n` tells the developer what kind of data this field expects (a short code vs a paragraph).
3. **Stay in sync with application-layer validation** (DTO / class-validator) and the UI (`maxLength`).
4. When you genuinely need long / unbounded strings → use `TEXT` directly (see section 6).

Therefore choosing `n` = "the realistic maximum **plus a safety margin**", not a byte-by-byte calculation.

## 1. Short enums / statuses — `VARCHAR(10)` and `VARCHAR(20)`

These are fields that only accept a fixed set of textual values.

| Column | Type | Actual values | Why this size |
|-----|------|-----------------|------------------------|
| `status` (many tables) | `VARCHAR(20)` | `ACTIVE`, `SUSPENDED`, `in_progress`, `cancelled` | Longest status ~ `SUSPENDED`/`in_progress` (11). Chose **20** as the common standard for every status column, for consistency and room for new statuses. |
| `action` (permissions) | `VARCHAR(20)` | `create`, `read`, `update`, `delete`, `manage` | CRUD verbs, longest 6 chars. 20 is plenty. |
| `otp_type`, `priority`, `urgency`, `severity`, `channel` | `VARCHAR(20)` | `login`, `routine`, `APP`, `SMS`... | Same group of short enums → follow the 20 standard. |
| `currency` (payment/service) | `VARCHAR(3)` or `VARCHAR(10)` | `VND`, `USD` | The **ISO 4217 standard = exactly 3 chars** → `VARCHAR(3)` is the most accurate (used in `treatment_plans.quote_currency`). Where `VARCHAR(10)` is used (`services.currency`) it is looser — **should be standardized to (3)** for consistency. |

**Key point, `gender` is not a VARCHAR at all.** It is a `SMALLINT` holding an ISO/IEC 5218 code — `0` unknown, `1` male, `2` female — with a `CHECK (gender IN (0,1,2))` on `users`, `patients` and `accounts`. Two bytes, numeric comparison, and the value set is enforced by the constraint rather than by a width. Labels live in code (`GENDER_LABELS`), not in the database. `blood_type` was removed from `patients` entirely.

## 2. Business codes — `VARCHAR(50)` / `VARCHAR(100)`

Codes generated by the system or business, with a prefix + number.

| Column | Type | Why |
|-----|------|--------|
| `patient_code`, `appointment_code`, `clinic_code`, `service_code`, `order_code`, `specialty_code` | `VARCHAR(50)` | Form `APPT-20260724-0001` / `PT-000123`. In practice < 25 chars; **50** is double the room for a long prefix + timestamp + sequence. |
| `username` | `VARCHAR(50)` | Login name, common UX limit 30–50. Long enough, blocks spam. |
| `role_name` | `VARCHAR(50)` | `RECEPTIONIST` (12) is the longest. 50 leaves room for new roles. |
| `permission_name` | `VARCHAR(100)` | Form `medical_record.update` / `appointment.cancel` — combines resource + action so longer than a normal code → 100. |
| `insurance_number`, `id_number`, `license_number`, `certification_number` | `VARCHAR(100)` | Legal / insurance document numbers have diverse formats per country → widened to 100. |
| `template_code`, `gateway_name` | `VARCHAR(100)` | `APPOINTMENT_REMINDER`, gateway names `SendGrid`/`Firebase` → 100 is safe. |

---

## 3. People names & administrative addresses — `VARCHAR(100)` / `VARCHAR(255)`

| Column | Type | Why |
|-----|------|--------|
| `full_name`, `clinic_name`, `service_name`, `specialty_name`, `medication_name`, `diagnosis_name` | `VARCHAR(255)` | **255** is the classic "magic number": before Postgres 9.1 it was the threshold for storing a 1-byte length header. Today it is just a common convention for "free-form but bounded name strings". Vietnamese person/organization names with diacritics fit comfortably. |
| `ward`, `district`, `city`, `relationship`, `body_location` | `VARCHAR(100)` | Names of administrative units / relationships ("Phường Bến Nghé", "biological child") — 100 is more than enough. |
| `email` | `VARCHAR(255)` | **RFC 5321** limits an email address to at most 254 chars → 255 is the correct standard. |

---

## 4. Phone numbers & network — `VARCHAR(20)` / `VARCHAR(45)`

| Column | Type | Why |
|-----|------|--------|
| `phone`, `emergency_phone` | `VARCHAR(20)` | E.164 numbers at most 15 digits + `+` prefix + possible spaces/`-`. **20** covers every international format. |
| `ip_address` | `VARCHAR(45)` | **45** = max length of an **IPv6** address in IPv4-mapped form (`0000:0000:...:255.255.255.255` = 45 chars). This is the standard value for storing an IP as text. |
| `otp_code` | `VARCHAR(10)` | OTP code of 4–8 digits → 10 leaves room. |

---

## 5. Currency & measurements — `NUMERIC(p,s)`

Money is **never** stored as `FLOAT/DOUBLE` (binary rounding error) → always `NUMERIC(precision, scale)`.

| Column | Type | Why |
|-----|------|--------|
| `amount`, `refund_amount` (payment) | `NUMERIC(12,2)` | `precision=12, scale=2` → max **9,999,999,999.99** (10 integer digits). Enough for a dental bill in VND (tens–hundreds of millions, with margin up to tens of billions). `scale=2` gives 2 decimals. *Note:* VND has no fractional part in practice, but (12,2) is kept for multi-currency flexibility (USD has cents). The VNPay gateway multiplies ×100 when sending. |
| `estimated_cost` (treatment_plan) | `NUMERIC(12,2)` | Quote for the whole treatment course → use a large precision like payment. |
| `base_price`, `custom_price`, `cost` (per service/procedure) | `NUMERIC(10,2)` | The price of **one** service is smaller than a total bill → `precision=10` (max ~99,999,999.99) is enough and leaner than (12,2). |

Rule: `precision` = total number of digits; `scale` = number of digits after the decimal point. `NUMERIC(12,2)` ⇒ 10 integer digits + 2 decimal digits.

---

## 6. When to use `TEXT` instead of `VARCHAR(n)`

Use `TEXT` for long content / content whose length can't be predicted — do not set a meaningless limit:

| Column | Why TEXT |
|-----|-------------|
| `address` | A full address can be very long, multi-line. |
| `notes`, `description`, `reason`, `chief_complaint`, `diagnosis`, `treatment_plan`, `present_illness`, `physical_examination` | Clinical notes / free-form descriptions — the doctor types as much as they want. |
| `access_token`, `refresh_token`, `logo_url`, `image_url`, `file_url`, `thumbnail_url` | Tokens/URLs of highly variable length (URLs with queries, presigned links are very long). |
| `allergies`, `chronic_diseases`, `tags` | `TEXT[]` — a multi-element array, each element free-form. |

Principle: **a clear business threshold → `VARCHAR(n)`; open content → `TEXT`.**

## 7. Other fixed types

| Column | Type | Why |
|-----|------|--------|
| `*_id` primary/foreign key | `UUID` | Resists ID guessing, safe for distributed generation across microservices (no need for a centralized incrementing key). Cross-service does not set hard FKs. |
| `date_of_birth`, work date | `DATE` | Only a date needed, no time. |
| `created_at`, `updated_at` | `TIMESTAMP` | Full timestamp, defaults to `CURRENT_TIMESTAMP`. |
| `is_primary`, `email_verified`, `phone_verified` | `BOOLEAN` | Binary flag. |
| `retry_count`, `max_retries` | `INT` | Small counter, `INT` (2 billion) is more than enough, no `BIGINT` needed. |
| `timestamp` (typeorm_metadata) | `BIGINT` | Epoch milliseconds (13 digits) exceeds `INT` → must be `BIGINT`. |
| `record_hash`, `token_hash`, `blockchain_hash`, `pacs_id`, `provider_user_id` | `VARCHAR(255)` | Hashes/external identifiers have a fixed-ish length (SHA-256 hex = 64) but set to 255 as a reserve for other algorithms. |
| `icd_code` | `VARCHAR(20)` | **ICD-10/11** code is at most ~7–8 chars (`S52.501A`) → 20 is a safe reserve. |
| `tooth_number` | `VARCHAR(10)` | FDI tooth notation (2 digits) or a range → 10 is enough. |
| `file_format`, `view_angle` | `VARCHAR(10)`/`(50)` | `JPEG`, `DICOM`, shooting angle `panoramic` → short codes. |
| `method` (idempotency) | `VARCHAR(10)` | HTTP verb: `DELETE` (6) is longest → 10. |
| `path` (idempotency) | `VARCHAR(512)` | API URL path can be long (many segments + id) → 512. |

## 8. Summary "formula" for choosing size

| Data type | Standard size used in SMILE |
|--------------|-----------------------------------|
| Very short enum/status | `VARCHAR(10)` (otp_code, tooth_number) — note `gender` is `SMALLINT`, not a varchar |
| Normal enum/status | `VARCHAR(20)` (status, channel, severity, action) |
| Business code | `VARCHAR(50)` |
| Combined code / document number | `VARCHAR(100)` |
| Phone number | `VARCHAR(20)` |
| IP | `VARCHAR(45)` |
| Email | `VARCHAR(255)` (RFC 5321) |
| Person / organization name | `VARCHAR(255)` |
| Money — total bill | `NUMERIC(12,2)` |
| Money — unit price | `NUMERIC(10,2)` |
| Currency (ISO) | `VARCHAR(3)` |
| Free text / URL / token | `TEXT` |
| ID | `UUID` |

> Reminder: for PostgreSQL, these numbers are **data-validation constraints**, not storage optimization. The goal is "wide enough not to block real data, narrow enough to block junk", and **consistent** across tables.

---

## 9. Inconsistencies to review (notes)

- `currency`: some places `VARCHAR(3)` (correct ISO 4217), some `VARCHAR(10)` — should be standardized to `(3)`.
- `name VARCHAR` (no `n`, TypeORM `migrations` table) — auto-generated by TypeORM, ignore.
- `accounts.role` is `VARCHAR(20)` (migration) — a `CHECK` constraint has been added so it only accepts the 6 RoleEnum values.

## 10. Columns with an added CHECK constraint (optimized via data integrity)

> Reminder: shrinking `VARCHAR(n)` does NOT save bytes in PostgreSQL. "Optimizing" a closed-value-set column = a **CHECK constraint** (only accepts valid values). The `VARCHAR` length stays as-is (changing length forces a table rewrite, useless). Values are normalized to UPPERCASE both in old data (migration) and new input (DTO `@Transform` + `@IsIn`).

| Column (table) | Constraint | Allowed values |
|---|---|---|
| `accounts.role` | `chk_accounts_role` | 6 RoleEnum |
| `users.gender`, `patients.gender`, `accounts.gender` | `chk_*_gender` | 0 (unknown), 1 (male), 2 (female) — ISO/IEC 5218 |
| `services.currency`, `payments.currency`, `treatment_plans.quote_currency` | `chk_*_currency` | VND, USD, EUR, JPY |
| `notifications/notification_preferences/notification_templates.channel`, `appointment_notification_logs.channel`, `appointment_reminder_preferences.channel` | `chk_*_channel` | SMS, EMAIL, PUSH, APP |

Migration: `AddEnumCheckConstraints` in each datasource (iam-user, emr-medical, emr-clinic, payment). Reused TS enums: `clinical-emr-service/src/utils/enums/{gender,currency,notification-channel}.enum.ts` and `iam-service/.../notifications/domain/notification-template.ts` (NotificationChannel).

*CHECK not yet applied* to status/priority/urgency/severity columns (large, frequently-changing value sets — consider later).
`accounts.gender` used to be a phantom column (mapped by the entity, absent from the DB). `AddAccountsGender1700000007000` creates it as `SMALLINT` with `chk_accounts_gender`. `accounts.full_name` is still a phantom and still needs its own migration.
